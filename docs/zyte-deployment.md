# Zyte Scrapy Cloud deployment

Project: **881056**. Deployment has not been executed by this project implementation.

## Deploy

From the repository root, using your own Scrapy Cloud account:

```bash
source .venv/bin/activate
python -m pip install shub
shub login
shub deploy 881056
```

`shub login` takes a **Scrapy Cloud API key**, not a Zyte API key. Do not commit credentials or paste them into project settings. See [Zyte's deployment tutorial](https://docs.zyte.com/web-scraping/tutorial/cloud.html) and [shub's deployment guide](https://shub.readthedocs.io/en/latest/deploying.html).

`scrapinghub.yml` selects `scrapy:2.14-20260217`; this is the stack used in Zyte's current tutorial when this repository was created. Stack availability and Python/runtime versions are platform-managed: check deployment output before production use. `requirements.txt` adds Pydantic, YAML, httpx, and tldextract; Scrapy/Twisted/lxml come from the stack. `setup.py` provides the legacy egg build compatibility used by shub, with package metadata in `pyproject.toml`.

Cloud also requires the `scrapy` entry-point group to expose `settings = reconspider.settings`. This is declared in `[project.entry-points.scrapy]` in `pyproject.toml` and included by setuptools in the deployment egg. `scrapy.cfg` alone does not supply that egg metadata. If deployment reports `Scrapy settings entrypoint is not found`, verify that this declaration is present and rebuild with `shub deploy 881056`. The packaging regression test builds an egg and loads its settings entry point using `importlib.metadata`.

## Job arguments

```bash
shub schedule 881056/universal -u 1 \
  -a target=https://example.com \
  -a max_depth=5 -a max_pages=1000 \
  -a rate_limit=0.5 -a concurrency=8 -a timeout=30
```

Multiple seeds and explicit scope:

```bash
shub schedule 881056/universal -u 1 \
  -a 'targets=["https://example.com","https://authorized.example.com"]' \
  -a 'scope_hosts=["*.authorized.example.com"]' \
  -a 'exclude=["/logout*","/delete*"]' \
  -a include_subdomains=false -a respect_robots=true
```

All CrawlConfig fields are accepted as validated job arguments. List fields accept JSON arrays or comma-separated values. Boolean strings are validated correctly (`false` is false). Alternatively use a JSON object with `-a config_json='{"targets":["https://example.com"],"max_pages":300}'`. No local scope/target file is needed or assumed in Cloud.

`output`, `sqlite`, and `jobdir` default to none in Cloud. Standard Scrapy items are yielded for the Cloud item collector, and `recon/*` stats expose dispatch/fetch counts, scope skips, extraction errors, and budgets. Local `run` metadata/duration records are generated by the local output pipeline; Cloud duration and final counts are available in platform job stats. Runtime paths are ephemeral: never assume a SQLite database or JOBDIR survives independent jobs.

## Retrieve and compare

```bash
shub items 881056/SPIDER_ID/JOB_ID > current.jsonl
reconspider report --input current.jsonl --output output/cloud
reconspider diff --old previous.jsonl --new current.jsonl --output comparison.json
```

The IDs in this example are placeholders; use the actual job identifier returned by `shub schedule`. Job items are the portable inventory. Retain them locally or use `reconspider sync push --file current.jsonl` with an HTTPS storage endpoint you configure. Cloud results do not depend on local file persistence.

## Periodic execution and single-unit resources

Configure periodic execution in the Scrapy Cloud dashboard if the project/plan exposes periodic jobs, or use an external scheduler calling `shub schedule 881056/universal ...`. See [Zyte periodic jobs documentation](https://docs.zyte.com/scrapy-cloud/usage/reference/http/periodicjobs.html). For example, `0 3 * * *` schedules a daily 03:00 UTC run (09:00 Asia/Dhaka); the documented API accepts simple values or `*` in each field, not ranges/steps/lists. Confirm the schedule timezone in the platform UI. Confirm current plan features, quotas, item retention, storage, and concurrent job availability before relying on them; no free-plan scheduling/storage entitlement is assumed here.

The lightweight default uses `-u 1`, static responses, a two-second per-domain minimum delay, one request per domain, global concurrency eight, depth five, a 1,000-attempt budget, a 2 MiB body cap, 20,000 discovery observations, and 1,000 extracted links per response. Memory warnings/termination are set at 512/768 MiB; adjust to the actual unit allowance. Defaults aim for modest resource use but are not a guarantee of the platform's unit capacity. Browser runtime is neither provisioned nor supported in this Cloud configuration.

## Verify a deployment

Check that the deployment output lists the spider, schedule a deliberately small **authorized** target job, inspect job logs/stats/items, and confirm scope/robots/address guards loaded. Use `shub log JOB_ID`, `shub requests JOB_ID`, and `shub items JOB_ID`. An egg build or local `scrapy list` check alone does not verify Cloud deployment or egress. The repo's tests run without Cloud credentials and do not claim those checks happened.
